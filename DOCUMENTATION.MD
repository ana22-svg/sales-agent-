This trades speed for recall. 1500 chars is roughly a quarter of what you had. If a page's relevant fact sits past character 1500 (common on long pages — the Notion customer-stories page, for instance, likely has case studies stacked well past that point), the model now never sees it. That's not a bug, it's a tradeoff — you're choosing "finish more checklist items, each with less of the page" over "read more of fewer pages." Worth stating that choice explicitly rather than letting it look like a pure win.
_OLLAMA_LOCK means your two workers were never actually running extraction in parallel. I noticed it in the code you pasted — every extract_relevant_fact() call serializes on that lock (makes sense, since the server log shows n_slots = 1, one inference slot). So MAX_WORKERS=2 parallelizes search()/fetch() but extraction has always been sequential. Not something to fix — a single-slot local model can't do otherwise — but worth a line in your writeup so it doesn't look like an oversight when someone reads the trace and notices extract events never overlap.
